    Fault injection

    Each fault asks for confirmation first. The caps below are enforced by the server.

    CPU spike

    Runs a busy loop in a background thread, so CPU jumps well above the baseline.

    What you will see: CPU crosses the alert line, an incident opens after {{ config.openAfter }} anomalous samples in a row, and it closes after {{ config.closeAfter }} normal ones.

    • {{ config.maxSpikeSec }} s at most
    • {{ config.cooldownSec }} s cooldown

    Memory leak

    Allocates {{ config.leakStepMb }} MB and holds it until it is released. Freed automatically after {{ (config.leakAutoReleaseSec // 60)|int }} minutes.

    What you will see: memory jumps by {{ config.leakStepMb }} MB and the incident stays open until the memory is released.

    0 of {{ config.leakLimitMb }} MB held
    • {{ config.leakStepMb }} MB a step, {{ config.leakLimitMb }} MB held at most
    • {{ config.cooldownSec }} s cooldown

    Database corruption

    Writes garbage over the SQLite file header, so every query fails until a snapshot is restored.

    What you will see: the next database check fails, an incident opens at once, and it stays open until a snapshot is restored in the Time Machine.

    • recoverable from a snapshot
    • {{ config.cooldownSec }} s cooldown

    Why it exists

    Most monitoring stops at the alert: a graph turns red and a person takes over. DeepBell is a small lab for what comes next. It decides that something is really wrong, writes down what happened, and gets the data back to a known good state, on a target small enough to break on purpose: its own process.

    Architecture

    Detect and report

    1. Sampler threadpsutil reads CPU and RSS every {{ config.sampleIntervalSec }} s
    2. Metrics storemetrics.db (SQLite)
    3. Detectorbaseline, Isolation Forest, consecutive-sample rule
    4. Incidents and reportstimeline with alerts and likely cause, reports/*.md

    Recover

    1. App databaseapp.db, sample transactions
    2. Snapshot threadcopies it every {{ config.snapshotIntervalSec }} s if it changed
    3. Snapshotsbackups/*.db.bak, newest {{ config.snapshotsKeep }}
    4. Rollbackfrom the Time Machine, the guided demo or the startup check

    Serve

    1. APIFastAPI in one uvicorn worker; all state lives in this process
    2. UIJinja template and plain JavaScript, polling /api/status every {{ config.sampleIntervalSec }} s

    Everything runs in one Python process. The full step-by-step flows are in docs/process-flows.md.

    Design decisions

    • Three gates before an incident. A sample must be {{ config.cpuDeltaPct|int }} CPU points or {{ config.ramDeltaMb|int }} MB above the baseline (95th-percentile CPU and median memory of the last 150 normal samples), the Isolation Forest must call it an outlier, and it must happen {{ config.openAfter }} samples in a row; {{ config.closeAfter }} normal samples close it. On its own the forest flagged ordinary jitter, and a fixed threshold alone ignores what normal looks like for this process.
    • Open incidents stay out of the baseline, so a leak that is still held never becomes the new normal.
    • Incident history lives in metrics.db, not app.db, so corrupting or rolling back the application database never rewrites it.
    • Caps and cooldowns for a public demo. CPU spikes last at most {{ config.maxSpikeSec }} s, leaks are {{ config.leakStepMb }} MB a step and {{ config.leakLimitMb }} MB in total, every fault has a {{ config.cooldownSec }} s shared cooldown, leaked memory is freed after {{ (config.leakAutoReleaseSec // 60)|int }} minutes, and the crash fault and API-key form are off. The guided demo runs on the server, one run at a time, so a closed tab cannot leave a fault behind.
    • A single worker by design. Telemetry, open incidents, cooldowns and leaked memory are process state. Running more workers would need a shared store, which this lab does not need.
    • Template reports by default. They are free, deterministic and testable; Gemini (through LangChain) is optional and falls back to the template on any error. Every report is labelled with what wrote it.

    Limitations

    • It monitors only itself, on two signals (CPU and resident memory). It is not a general monitoring tool.
    • The minimum deviations are fixed, so smaller spikes and leaks are deliberately ignored.
    • Snapshots are not point-in-time recovery: a rollback loses whatever changed since the snapshot.
    • At runtime the rollback is manual (or part of the guided demo); it is automatic only in the startup check.
    • There is no authentication. Public demo mode caps the damage, but any visitor can inject the capped faults.
    • Times to detect and recover are measured on injected faults in this lab and say nothing about a production system.
    • On the free hosting plan the disk is ephemeral, so history resets when the service restarts.
